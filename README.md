# НарядAI — интеллектуальная система выдачи и контроля нарядов

**«Наряд выдан — ИИ на контроле».** Кейс № 1 АО «Костанайские Минералы», Qostanai AI Industry Hackathon 2026.

Мастер выдаёт наряд с телефона за несколько нажатий. Исполнители получают его push-уведомлением, принимают и закрывают у себя: работы, шифр, материалы, фото «после». ИИ при этом:
- следит за сроками;
- проверяет качество закрытия и сравнивает фото «до/после»;
- подбирает исполнителя;
- считает рейтинг;
- находит проблемное оборудование по истории.

Решение — устанавливаемое веб-приложение (PWA) для телефона и компьютера с общей базой и ролями: мастер, исполнитель, руководитель, администратор.

## Что сделано по ТЗ

| Раздел ТЗ | Что реализовано |
|---|---|
| **5.1 Выдача наряда** (MVP) | Карточка со всеми полями; фото «до» (до 5, сжатие на телефоне); голосовой ввод; **быстрый наряд** за 5 нажатий: фото → оборудование (или QR) → «Аварийный» → «Выдать»; исполнитель подбирается автоматически. Переназначение, отмена, смена приоритета — с записью в историю |
| 5.1.2 Статус исполнителя при выборе | «Свободен / Выполняет № / В очереди N / Не на смене» прямо в списке |
| 5.1.3 ИИ-подбор исполнителя | Ранжирование: доступность, специальность под шифр, опыт на этом и похожем оборудовании, рейтинг, разряд. Каждому кандидату — объяснение причины |
| 5.1.4 Подсказка шифра и норматива | По описанию проблемы, кнопка «Применить норматив» |
| **5.2 Панель мастера** (MVP) | Цвета статусов по ТЗ (зелёный / жёлтый / синий / серый) с легендой; доска по колонкам «Просроченные, Выданные, Принятые, В очереди, В работе, Проверка, Выполненные за смену»; фильтры; счётчики смены (выдано, выполнено, просрочено, оборудование в простое) |
| **5.3 Приложение исполнителя** (MVP) | Push со звуком; аварийный наряд — красное полноэкранное окно с кнопкой «Принять». Все кнопки статусов: отказ и пауза с причиной. Форма закрытия: работы (голосом), шифр, материалы с количеством, фото «после», комментарий. Своя очередь, сроки и оценка по каждому наряду. **Работа без сети**: действия и фото копятся на телефоне и отправляются при появлении связи |
| 5.4 Справочники | Участки, оборудование, сотрудники, бригады, шифры М/Э/Г/П/С, материалы, нормативы — редактирует администратор |
| 5.5 История | Каждое действие: кто, что, когда. Полная история по оборудованию в отчётах и у ассистента |
| **6.1 ИИ-контроль сроков** (MVP) | Сервер проверяет сроки раз в минуту (Cron) и при работе приложения. Сценарии: напоминание до срока, сообщение о просрочке исполнителю и мастеру в формате ТЗ, эскалация «не принят за 10 / 3 мин» с предложением замены, повторы, уведомление руководителю. **Пороги настраиваются** |
| **6.2 ИИ-проверка выполнения** (MVP) | Мгновенная проверка правилами плюс фоновая проверка языковой моделью. Вердикт: принято / с замечаниями / доработка |
| **6.3 Анализ фото** | dHash сравнивает «после» с «до» и прежними снимками. Дата съёмки берётся из EXIF. Мультимодальная модель сравнивает «до/после», оценивает 1–5. При низкой уверенности ставит «нужна проверка мастером» |
| **6.4 Отчёт по наряду** (MVP) | Исполнителю: оценка, что сделано хорошо, что улучшить, время против норматива. Мастеру: полный разбор, факты проверки ИИ, фото «до/после» рядом. Мастер может изменить оценку — финальное решение за ним |
| **6.5 Аналитика и аномалии** | Частые отказы; повтор шифра после ремонта; отказы после ППР; связь со сменой; доработки исполнителя; перерасход бригады; **рост отказов с прогнозом** |
| **6.6 Рейтинг** (MVP) | Исполнители и бригады за любой период, составляющие на графике, пояснение каждому: «из чего сложился рейтинг» |
| 6.7 ИИ-ассистент (бонус) | Чат с голосовым вводом: «Кто свободен из электриков?», «Что просрочено?», «Отчёт за неделю по обогащению» |
| **7 Отчёты** | За смену, сутки, неделю, месяц, свой период; фильтры: участок, оборудование, исполнитель, бригада. Наряд, смена (загрузка людей + сводка ИИ), рейтинги, материалы, простои, аномалии. **Excel (8 листов) и PDF**. Дашборд руководителя |
| Бонусы | Голосовой ввод; ассистент; прогноз отказов; **QR-коды** на оборудовании (печать этикеток, сканер); **казахский язык** интерфейса исполнителя |

## ИИ-модули: как это работает

Каждый модуль работает и без внешней модели, а с подключённой LLM становится «умнее». В интерфейсе всегда видно, чем сделана оценка: «ИИ-анализ», «проверка по правилам» или «статистика».

| Модуль | Без LLM | С LLM (Claude / OpenAI) |
|---|---|---|
| Контроль сроков | Полностью: правила и Cron | — |
| Проверка отчёта | Полнота; фото; перерасход материалов против ориентира; материалы, нетипичные для шифра; время против норматива | Плюс: соответствие работ проблеме, логичность материалов, фото «до/после» (то же оборудование, устранено ли, аккуратность, кожухи), оценка и уверенность |
| Фото | dHash и EXIF | Мультимодальное сравнение |
| Подбор исполнителя, шифр | Скоринговая модель на истории | — |
| Аналитика | Статистика и правила с порогами и поддержкой | Сводка периода простым языком и рекомендации |
| Ассистент | Распознавание намерения по правилам, ответы из данных | Модель сама вызывает инструменты (tool use) |

- **Модель:** по умолчанию Claude Opus 5.5 (`AI_PROVIDER=claude`, ключ `ANTHROPIC_API_KEY`), поддерживается OpenAI. Модель проверяет отчёт в фоне и не задерживает исполнителя.
- **Обезличивание:** ФИО (с учётом падежей), телефоны и e-mail заменяются метками до отправки во внешний сервис. В ассистенте и сводках имена заменяются кодами и подставляются обратно уже у нас.
- **Передача фото:** изображения отправляются внешней модели только при `AI_PHOTOS_APPROVED=true` в конфигурации развёртывания. Без этого разрешения, при неполной передаче изображений и в режиме `mock` визуальную проверку выполняет мастер; оценка по фото равна 0. Ответ модели проходит строгую проверку полей и диапазонов.
- **Решение за человеком:** модель только рекомендует. Вернуть наряд на доработку ИИ может только до решения мастера и только при уверенности ≥ 70%.

## Рейтинг исполнителей и бригад

`Рейтинг = 50·(качество/5) + 30·доля_в_срок + 15·(1 − доля_доработок_и_повторов) + 5·объём − штраф`

| Составляющая | Вес | Почему |
|---|---|---|
| Качество (оценка мастера, иначе ИИ) | 50 | Главная цель ремонта — исправное оборудование: некачественная работа порождает повторные простои |
| Выполнено в срок | 30 | Простой оборудования — прямые потери производства |
| Без доработок и повторного отказа за 7 дней | 15 | Ремонт должен устранять причину, а не следствие |
| Объём с учётом сложности | 5 | Ценит загрузку и сложные наряды, но не поощряет гонку за количеством |
| Отказ без уважительной причины | −2 за каждый, до −10 | Уважительность причины отмечает мастер, поэтому штраф справедлив |

## Данные

Сущности ТЗ (раздел 8) хранятся в D1 (SQLite):
- участок, оборудование, сотрудник, наряд;
- событие наряда (`history`), фото (R2 + метаданные), списание материала (`report.materials`), оценка ИИ (`check`, `masterScore`).

**Тестовый набор** — генератор `lib/history-seed.ts`. Администратор загружает его кнопкой «Загрузить историю» и так же удаляет. Состав:
- 4 участка, 25 единиц оборудования, 2 мастера, 15 исполнителей в 3 бригадах;
- 20 шифров, 40 материалов;
- **570+ нарядов за 90 дней**.

Заложено 6 закономерностей, все находит аналитика (тест `tests/analytics_api.py`):
1. Конвейер К-3 ломается примерно в 3 раза чаще среднего, в основном шифр М-02 (подшипник).
2. Исполнитель Арман Алиев — частые доработки и повторные отказы.
3. На дроблении ночью отказов в 2–3 раза больше.
4. Мельница МШЦ-3600 отказывает вскоре после ППР.
5. Бригада 3 перерасходует материалы.
6. Число отказов конвейера К-12 растёт месяц к месяцу — прогноз отказа.

## Архитектура

```
Телефоны и ПК (PWA, офлайн-очередь, Web Push)
        │  HTTPS, опрос раз в 4 с (≤ 5 с по ТЗ)
        ▼
Cloudflare Worker — Next.js (vinext): /api/service, /api/analytics, /api/assistant, /api/photo
        │                       │                     │
   D1 (SQLite)            R2 (фото)          Cron раз в минуту → контроль сроков, push
        │
   LLM API (Claude / OpenAI) — только обезличенные данные
```

- **Масштабирование.** Worker без состояния. Телефоны получают только текущие наряды, тяжёлая аналитика считается на сервере.
- **Интеграция.** Выгрузка нарядов для 1С / ERP / ТОиР: `GET /api/integration/orders?from=…&to=…&format=json|csv`. Доступ по сервисному токену `INTEGRATION_TOKEN`. Справочники можно синхронизировать в обратную сторону — у оборудования хранится инвентарный номер.

## Безопасность

- Пароли — PBKDF2-SHA256 с солью. Сессии — HttpOnly / Secure / SameSite=Strict, отзываются при блокировке и смене пароля. Есть лимит попыток входа.
- Роли и доступ к нарядам и фото проверяет сервер: исполнитель видит только свои наряды.
- В push-службу не уходит ни имён, ни производственных данных: уведомление пустое, текст подтягивается с нашего сервера по сессии.
- Секреты хранятся только в настройках хостинга. Файлы `.dev.vars*` и `.cloudflare.local.json` в репозиторий не попадают.

## Запуск локально

Нужен Node.js 22.13 или новее и Python 3 с Pillow (для тестов).

```sh
npm ci
cp .env.example .dev.vars   # заполните INITIAL_USERS (пароли от 8 символов)
npm run build
npm run db:local
npm run start:local          # http://127.0.0.1:4173
```

Для проверки конвейера ИИ без внешнего ключа добавьте в `.dev.vars` строку `AI_PROVIDER=mock`.

**Тесты** (при запущенном `start:local`, только локальная база):
```sh
python tests/team_api.py        # роли, фото, жизненный цикл, администрирование
python tests/assignment_api.py  # отказ → переназначение, ИИ-подбор, уведомления, пороги
python tests/ai_review_api.py   # фоновая ИИ-проверка (AI_PROVIDER=mock)
python tests/photo_checks_api.py
python tests/analytics_api.py   # история и все закономерности
python tests/assistant_api.py   # вопросы ассистенту из ТЗ
python tests/deadline_api.py
python tests/workcards_api.py
```

## Проверки интеграции

`npm run typecheck`, `npm run test:quality` и `npm run build` проверяют типы, правила, FIFO, подбор исполнителя, аналитические срезы и реальную выгрузку восьми листов XLSX. Для `test:quality` достаточно Python 3 без дополнительных пакетов.

`npm run test:quality-api` запускайте с `DEMO_ONLY=true` и `WORKSPACE_MODE=false` в `.dev.vars` при работающем локальном сервере. Тест создаёт отдельную демо-сессию и проверяет роли, очередь, одновременные старты нарядов, совместимость с карточками работ, фото, приёмку и просрочки. Адрес задаётся через `NARYADAI_ORIGIN`; разрешён только localhost.

Подробности объединения и выполненных проверок: [docs/MERGE_NOTES.md](docs/MERGE_NOTES.md).

## Развёртывание

- **Cloudflare (основное).**
  1. Выполните `npx wrangler login`.
  2. Создайте `.dev.vars.production` с секретами (WORKSPACE_MODE, INITIAL_USERS, ANTHROPIC_API_KEY, REMINDER_TOKEN, INTEGRATION_TOKEN, PUBLIC_ORIGIN).
  3. Запустите `npm run deploy:cf`. Скрипт сам создаст D1 и R2, применит миграции, опубликует Worker с Cron и загрузит секреты.
- **ChatGPT Sites.** `powershell -ExecutionPolicy Bypass -File scripts/pack-sites.ps1` собирает архив в формате площадки, без секретов. Секреты задаются в настройках проекта Sites.

## Ограничения

- Доставку push, время загрузки фото по мобильной сети и скорость выдачи наряда нужно подтвердить на физических телефонах перед защитой. На iPhone push работает только у приложения, установленного на главный экран.
- Сканер QR в браузере работает в Chrome на Android. На других устройствах наклейку открывает обычная камера телефона по ссылке.
- Перевод на казахский покрывает экраны исполнителя. Нужна вычитка носителем языка.
- История в демонстрационном наборе синтетическая. Если заказчик даст обезличенные реальные данные, аналитика примет их без изменений.
